## 1. 设计语言（与 WP-2 同源）

- **token**：强调 `#007AFF` / 正常 `#34C759` / 注意 `#FF9500` / 危险 `#FF3B30`；深色底 `#1C1C1E`·面板 `#2C2C2E`·浮起 `#3A3A3C`；浅色底 `#ECECF0`·面板 `#FFF`。圆角卡片 12 / 控件 8。
- **材质**：统一 1px 描边分层（深色为白 9% / 浅色为黑 8%），无渐变、无发光，仅颜色过渡；数字一律 tabular-nums（速率/百分比不抖动）。
- **字体**：系统字体栈（零 webfont）。中文优先（zh 文案随 arb 走）。
- **状态语义**：`●` 绿=运行/在线 · 橙=注意 · 红=危险/离线 · 灰=未安装/停用；数字单位 ≤4 字符（MB/s、GB、°C）。
- **图标**：占位线稿（1.8–1.9px 线宽与主题侧栏一致）；最终拟以 WP-2 Logo 家族统一出图（应用图标复用切面宝石）。

## 3. 交互约定

- **导航**：底部四 tab（概览/设备/系统/设置）；配对前为无 tab 的单任务流。
- **数据刷新**：前台 5s 轮询（契约 §5）；下拉刷新手动补取；后台停取、回前台立即补一次。
- **控制反馈**：动作中行内 loading；成功后 ≤2s 快照自动反映（WP-4 §12.4 承诺），失败按 `action_failed.detail` 展示。
- **危险动作**：底部确认层（⑦）；连断动作（停网络/SSH 类）v1 不进 UI。
- **空态/降级**：不白屏（⑨）；指纹变化（重刷固件）→ 阻断连接 + 引导重配对。

## 4. 可扩展性设计（扩展模型）

**目标**：路由器侧持续长新东西（daemon 新节、新插件服务、WP-8 Bridge 新动作、WP-9 OTA），App **不因新功能重做布局**；新功能的分级成本：`0 行` → `1 条注册表项` → `1 个页面模块`。

### 4.1 四层扩展阶梯

| 层 | 机制（路由器侧供给） | App 侧成本 | 体现 |
| :-- | :--- | :--- | :--- |
| **L0 数据容忍** | 契约加法/未知键（`services` 开放映射、未知节字段） | **0 行**（模型层已容忍，W6.1 已就位） | 新字段/新服务到达不崩、不丢整页 |
| **L1 泛化渲染兜底** | 新 daemon 节 / 新服务键（WP-4 探针描述文件，**零重编**） | **0 行** | 未知节 → 「通用 KV 卡」（⑩：节名 + 标量键值行，≤6 行超限进详情）；未知服务 → 泛化行（title + 状态点） |
| **L2 注册表增强** | 同上（要更好的呈现时） | **1 条注册表项** | bespoke 卡片（如 sparkline 网络卡）；服务富化行（如 OpenClash 带 core 版本）；动作条目 |
| **L3 新页面模块** | 新功能域（配置流/详情/多步操作，WP-8 Bridge / WP-9） | **1 个 feature 模块 + 1 条路由** | 服务详情（⑪）、DDNS 配置页、固件升级页 |

### 4.2 代码机制（W6.3 实施规范）

- **卡片注册表**：`lib/features/overview/cards/` 每个卡一个文件，暴露 `CardSpec{id, order, visible(Snapshot), build(ctx, Snapshot)}`；`registry.dart` 汇总为列表——新卡=加文件+一行。可见性谓词统一处理「节缺失/节 null」（Docker 卡即此机制）。
- **通用兜底卡**：注册表渲染后，对快照中**未被任何 CardSpec 消费**的顶层节，自动追加通用 KV 卡（节名标题 + 标量/短数组字段行，嵌套对象一行展开 `k: v1/v2`；超 6 行进详情页）。——新节「至少可见」由机制保证，不依赖开发者记得改 App。
- **服务列表 spec**：`ServiceRowSpec{id, title(ctx, data), enrich(data)}` + **默认泛化行**（title 优先取数据 `title` 字段 → i18n 映射 → id 原样；`running` 状态点；其馀标量字段作为副文本）。富化行仅覆盖 title/enrich 两处。
- **动作能力注册表**：`ActionSpec{id, label, danger?, confirmText?, params?, enabled(snapshot), run(client)}`；页面（系统页动作区/服务详情页）**只渲染注册表**，不写死单项。WP-5 白名单或 WP-8 Bridge 新增动作 → 加一条注册表项 + arb 文案。
- **路由**：go_router 声明式路由表；详情页路径 `/<tab>/<feature>/<id>`；新页面=加路由条目，不触碰既有页面。
- **注册位置**：`lib/features/registry.dart` 单点聚合（cards/services/actions 三张表），评审友好（一次 diff 看到"新功能做了什么"）。

### 4.3 信息架构留位（布局层面的扩展性）

- **tab 数固定（4 个），不随功能增长**：tab = 稳定领域（概览/设备/系统/设置）；**新功能不新开 tab**，以三类落点进入：
  1. 概览**卡**（数据展示类，如新节）；
  2. 既有 tab 的**行**（管理/动作类，如系统页维护动作）；
  3. **详情页/配置页**（自既有行点击进入，如服务详情、DDNS 配置、固件升级）。
- **加 tab 的门槛（纪律）**：仅当新领域满足「多页面 + 独立上下文 + 高频入口」三条（例如未来若做「流量分析」大域）才评估第五 tab——需要走设计评审，不默认允许。
- **概览天然可增长**：卡片纵向滚动，注册表追加即增长；排序/显隐（「编辑」）后置，不阻塞扩展。
- **第三方插件无专属 UI 的兜底**：全部经 ⑩⑪ 模式（泛化行 → 详情页 → 动作注册表）获得"可见 + 可控"，与 TDD §5「能力下沉 API、UI 只消费 API」一致——App 不解析插件私有数据，不做 webview 嵌 LuCI 页。

### 4.4 边界（明确不做）

- **不做运行时 UI 下发**（服务端描述 UI/动态表单引擎）：App 是编译产物，扩展=发版；把发版成本压到"注册表加一条"即够（与 WP-3「运行时 widget 后置」同款判断）。
- **不做 webview 化插件页**（嵌入 LuCI 页面）：破坏多端一致与体验基线，与 TDD §5 冲突。
- **不为单插件开私路**：新功能必须走契约/动作面；无处安放说明路由器侧 API 缺位，应补 API 而非在 App 打洞。

### 4.5 端到端走查（三类扩展各一例）

1. **daemon 新节**（未来「wireless」节）：契约加法 → App **零改动**即出通用 KV 卡（⑩）→ 想要 sparkline/信道图时补 1 个 CardSpec。
2. **新插件（模式 B）**：WP-8 做 `quartz-ddns-bridge` → daemon 投探针描述文件（WP-4 §13，零重编）→ `services.ddns` 出现在快照 → App 服务卡泛化行自动显示；WP-5 动作表加 `ddns.update` → App 注册表加一条 → 服务详情页出现「立即更新」。
3. **top-level 新功能**：WP-9 OTA → 系统页加一行「固件更新 ›」（注册表）+ 1 个固件升级页（模块 + 路由）——tab 结构不变、其它页零改动。
